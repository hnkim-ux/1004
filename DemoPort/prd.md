## 1. 개요

### 1.1 목적
QA SW 엔지니어로서의 역량과 경력, 특히 **전장(차량 전자/전기 시스템) 검증** 전문성을 효과적으로 보여주는 개인 개발자 프로필 웹사이트를 구축한다.

### 1.2 배경
- 채용 담당자, 협업 파트너, 고객사에 본인의 검증 역량을 한눈에 전달할 수 있는 창구가 필요하다.
- 일반적인 개발자 포트폴리오와 달리, QA/검증 업무는 결과물이 눈에 잘 보이지 않으므로 **검증 프로세스, 사용 도구, 표준 준수 경험, 성과 지표**를 구조적으로 보여주는 것이 핵심이다.

### 1.3 목표
1. 방문자가 30초 안에 "전장 검증 전문 QA 엔지니어"임을 인지한다.
2. 주요 프로젝트와 검증 경험을 구체적인 사례로 확인할 수 있다.
3. 이메일을 통해 쉽게 연락할 수 있다.

## 4. 기능 요구사항

### 4.1 페이지 구성 (싱글 페이지 + 섹션 스크롤)

| # | 섹션 | 내용 | 우선순위 |
|---|---|---|---|
| 1 | Hero | 이름, 한 줄 소개("전장 검증 전문 QA SW 엔지니어"), CTA(연락하기) | P0 |
| 2 | About | 자기소개, 업무 철학, 핵심 역량 요약 | P0 |
| 3 | Expertise | 전장 검증 전문 영역 (아래 4.2 참고) | P0 |
| 4 | Skills & Tools | 검증 도구, 언어, 프레임워크, 표준 | P0 |
| 5 | Projects | 주요 프로젝트 카드 (역할, 대상 시스템, 검증 범위, 성과) | P0 |
| 6 | Experience | 경력 타임라인 | P1 |
| 7 | Certifications | 자격증 (ISTQB 등) | P2 |
| 8 | Contact | 이메일(mailto 링크), 이메일 복사 버튼 | P0 |

### 4.2 Expertise 섹션 상세 (전장 검증)
아래 항목 중 실제 경험에 맞춰 선택·수정한다.
- **검증 레벨**: SW 단위/통합 테스트, HILS(Hardware-in-the-Loop), SILS/MIL, 실차 검증
- **통신 프로토콜**: CAN / CAN-FD, LIN, Automotive Ethernet, UDS 진단
- **표준·프로세스**: ASPICE, ISO 26262(기능안전), ISO 21434(사이버보안)
- **도구**: Vector CANoe/CANalyzer, dSPACE, CAPL, Python 테스트 자동화
- **산출물**: 테스트 명세서, 요구사항 추적성(Traceability), 결함 리포트

### 4.3 Projects 카드 필드
- 프로젝트명 / 기간
- 대상 시스템 (예: BCM, ADAS, 인포테인먼트, 클러스터 등)
- 역할 및 책임
- 사용 도구·환경
- 성과 지표 (예: 테스트 케이스 수, 자동화율, 결함 검출 건수, 검증 기간 단축률)

### 4.4 공통 기능
- 반응형 레이아웃 (모바일 / 태블릿 / 데스크톱)
- 다크 모드 / 라이트 모드 전환
- 상단 고정 네비게이션 (섹션 앵커 이동)
- 이메일 복사 버튼 (클릭 시 클립보드 복사 + 토스트 알림)
- (P2) 한국어 / 영어 전환

## 6. 기술 스택 (제안)

- **구성**: 정적 사이트 (HTML / CSS / JavaScript) — 추후 필요 시 React/Next.js로 확장
- **스타일**: CSS 변수 기반 테마 (다크/라이트)
- **배포**: GitHub Pages 또는 Vercel
- **테스트**: Playwright 기반 E2E 스모크 테스트 (링크, 반응형, 다크 모드)

## 7. 디자인 방향

- **톤**: 신뢰감, 정밀함, 엔지니어링 — 깔끔하고 절제된 디자인
- **컬러**: 다크 네이비 / 그레이 기반 + 포인트 컬러 1개 (예: 시안 또는 오토모티브 레드)
- **모티프**: 계측기·대시보드·신호 파형 등 전장 검증을 연상시키는 미니멀 그래픽 요소
- **타이포**: 본문 Pretendard, 코드/수치 표기용 모노스페이스 폰트
